## Context

**Starting point.** `C:\Users\b.recoules\Downloads\_projets\AI-bookmark-manager` is a small AI Studio app (React 19 + Vite 6 + Express 5, `tsx server.ts`). It stores a flat `Bookmark[]` in `localStorage`, batches URLs (3 per call, 4 s apart) to a server-side Gemini endpoint (`/api/gemini/generate-bookmarks`, with Google Search grounding and a 5-step model/tool-shedding fallback), fetches per-platform context through a generic `/api/proxy` (X syndication/oEmbed, Threads oEmbed + meta scraping, YouTube oEmbed + HTML meta + playlist titles, generic OpenGraph), exports to Notion (schema enforcement, URL dedupe, 3 rps throttle) and to JSON/CSV/Markdown/HTML/Netscape bookmark files.

**What the user wants.** Branch from it and build a *full* local-first, private, peer-to-peer AI bookmark manager:

- Local-first, all data on device; optional Gemini or Claude API key, local models by default.
- AI analysis + summaries for any link type (web, PDF, video, social posts, files).
- Clustering by tags/themes; exploratory dataviz (theme stats, overlap/intersection maps); "Pearltrees"-style navigable trees generated from a search and AI-generated themes depending on context.
- Web fetch + local RAG to interrogate a group of links.
- P2P sharing with known users and groups of friends.
- Full editing of the whole database; PDFs and all link kinds.
- Import from Notion databases (plus browser/Pocket/Raindrop/Karakeep exports).
- "Training on the local database to improve search".
- A new database model (the flat localStorage array cannot support any of the above).

**Why now / intended outcome.** The current app already proves the value of AI-enriched bookmarks but is cloud-bound (server-side Gemini key), single-device, non-shareable, and un-queryable. The outcome is a desktop-first app (with the same React UI lineage) whose data lives in a local embedded database with vector + full-text search, is enriched by local models, is explorable visually, and can be shared selectively with friends over P2P without a mandatory server.

## Fixed constraints (user decisions, 2026-09-12)

- **Repo:** new long-lived branch in the existing `AI-bookmark-manager` repo (same remote); heavy restructuring on that branch.
- **Audience:** the user plus a few **non-technical friends**. They need signed installers, zero-config connection (invite link / QR), and local AI that works without any manual setup.
- **Shell:** Electron or similar, **one code base for Windows, Linux, macOS**.
- **Hardware floor for local inference:** RTX 3050 laptop (4 GB VRAM, Windows) and Apple M1 with 16 GB RAM. Small models by default, bigger models optional.
- **Scale:** 10k-100k links, everything local, only a chosen subset shared.
- **"Training on the local database"** means AI *reasoning over the data*: self-reorganisation of tags, Pearltrees-style trees of links in similar themes. Not model fine-tuning.
- **Language:** UI in French and English (i18n from day one).

## Research findings (The Doubtful + The Expert, 2026-09-12)

Full reports: `scratchpad/research/01-the-doubtful.md`, `02-the-expert.md` (to be copied into the repo under `plans/research/`).

**Does it exist?** Mostly yes, in pieces. Karakeep (AGPL, 29k stars) covers ~8 of the 12 features (local Ollama tagging/summaries, PDFs, OCR, archival, extension-side SingleFile crawling, MCP server, embeddings + hybrid search in 0.33, chat landing). Linkwarden, Readeck, Khoj, SurfSense, Obsidian + Web Clipper + Smart Connections, Anytype, Armaria, Raindrop, mymind, Are.na, Pearltrees each cover a slice. **Nothing ships the empty quadrant: an embedding map, cluster statistics, tag overlap/intersection maps, query-time theme trees, over a local corpus, plus honest provenance on AI output.** Nothing local-first does friend/group sharing without a server. Verdict from both agents: do not fork Karakeep (server product, Next.js + Meilisearch + Puppeteer); build, and optionally read Karakeep/Raindrop via API/MCP.

**Numbers that shape the design** (calibrated estimates, benchmark before committing):
- Generation on RTX 3050 4 GB: 1B–4B models only. Qwen3.5-4B Q4_K_M ~30–45 tok/s (Vulkan), Gemma 4 E2B ~55–80 tok/s. M1 16 GB: Qwen3.5-4B ~15–22 tok/s. A 400-token structured summary = 9–27 s. **100k links × 10 s ≈ 12 days of continuous inference.** Realistic nightly budget: 1–2k generation calls.
- Embeddings: EmbeddingGemma-300M (ONNX q8, 200 MB, 768-d Matryoshka → 256-d, FR/EN) at ~15–40 chunks/s on CPU. 100k links × ~8 chunks = 800k chunks ≈ 9 h once. Search/clustering/trees/map need only embeddings.
- Vectors: sqlite-vec brute force at 100k × 256-d ≈ 40–90 ms exact; usearch HNSW for 800k chunks with mmap `view()`. No ANN needed at doc level.
- Storage: 100k × 30 KB text ≈ 3 GB; page snapshots ~400–500 KB each ≈ 40–50 GB. Snapshots must be files, opt-in, never synced.
- Signing: Windows OV cert on hardware token ≈ €130–400/yr (EV €400–600; Azure Artifact Signing likely US/CA-gated); Apple Developer €99/yr. Unsigned = SmartScreen/Gatekeeper walls that lose non-technical friends.

**Key technical picks (Expert, verified versions Sept 2026):** Electron 44 (Chromium 152 / Node 24), electron-vite + electron-builder + electron-updater (artlux pattern); better-sqlite3 13 + FTS5 (`remove_diacritics 2`) + sqlite-vec 0.1.9 + usearch 2.26; Loro 1.16 (movable tree CRDT) one doc per collection, SQLite as derived index; iroh 1.0 via `@number0/iroh` 1.1 (QUIC, relays, tickets) + Trystero 0.25 (Nostr) for browser peers + NIP-44 Nostr mailbox for catch-up; node-llama-cpp 3.20 in an Electron `utilityProcess` with Vulkan/Metal/CPU builds (CUDA prebuilds need CUDA Toolkit 13.1 on the user machine, so not default); transformers.js 4.2 + onnxruntime-node for embeddings; Vercel AI SDK 7 for Gemini/Claude/Ollama abstraction with Zod schemas; defuddle 0.19 → readability 0.6 → hidden BrowserWindow → MV3 extension → Wayback for acquisition; unpdf 1.8 for PDFs; youtubei.js 18 + FxEmbed for platforms; graphology + Louvain multi-resolution for clustering; c-TF-IDF terms; LLM labels per cluster (~1.5–2k calls for 100k links); umap-js on 8–10k landmarks + inverse-distance placement for the map; deck.gl 9.4 scatter, sigma 3 for subgraphs, d3-hierarchy on Canvas, Observable Plot; Vitest 5, fast-check 4 (CRDT convergence), Playwright `_electron`, golden fixtures + weekly canary, a 100k-link fixture DB.

**Licensing traps:** Cosmograph is CC-BY-NC (avoid); UpSet.js has a non-standard dual license (verify); Kuzu is dead (Apple acquisition); sqlite-vss abandoned; cr-sqlite stalled; Firecrawl AGPL.

**Where the two agents differ (settled by The Pragmatic below):** live CRDT sync (Expert) vs encrypted share bundles through a self-hosted mailbox (Doubtful); bundling node-llama-cpp in the installer (Expert) vs embeddings-only bundled with generation external (Doubtful); Loro from day one vs SQLite first with a CRDT-compatible schema.

**Both agree:** the wedge and 4-week demo is the embedding map + cluster statistics + "ask this selection"; never an LLM call on the save path; LLM cost must scale with clusters, not documents; tag/tree reorganisation is a review queue with diff and undo, never auto-applied; the browser extension is the only reliable fetcher for logged-in/bot-walled pages; free-tier Gemini keys train Google models (warn loudly, default to local or Anthropic); Notion API import is expensive (2025-09-03 data-source API, 3 rps, lossy) and should be scoped, with CSV/HTML first.

## Technical design (The Builder, 2026-09-12)

Full design (1,970 lines: DDL for 24 tables, TS interfaces, IPC table, configs, data flows, test harness, v2 hooks): `plans/TECHNICAL-DESIGN.md` in the repo.

**Three structural choices:**
1. **Hexagonal ports.** `packages/core` never acquires anything; it takes `DbHandle`, `FetchLike`, `FileStore`, `Clock`, `Random`, `SecretStore` as arguments. better-sqlite3, undici, onnxruntime-node and Electron live only in `apps/desktop/src/main`. `packages/core` omits `@types/node`, so `node:` imports fail at typecheck before lint.
2. **One net chokepoint.** `apps/desktop/src/main/net/` is the only module allowed to import `undici`/`fetch`; every outbound byte passes `withEgress()`, so `egress_log` completeness is a lint rule.
3. **Undo is a forward op.** Reverting a run appends inverse ops with fresh HLCs; history is never deleted. This is what lets the v1 op log become a Loro doc in P9 without a semantic migration.

**Three ESLint firewalls (`eslint.config.js`) plus an arch test:** (A) no `node:`/host deps/React in `packages/core`; (B) the invariant: `pipeline/save`, `acquisition`, `embedding`, `chunker`, `importers` and the main-process save IPC cannot import `generation`; (C) nothing outside `main/net` imports `undici`/`node:http`. `arch.invariants.test.ts` walks the import graph (es-module-lexer) so the rule cannot be silently disabled.
